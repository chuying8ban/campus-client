# 校园助手 3.4.43 —— 动态主题为什么糊，以及 SVG 为什么救不了

## 先说结论
糊的根因不是"用了位图、没用矢量"，而是 **RemoteViews 的位图必须连像素一起走 binder**。
一次 `updateAppWidget` 里所有位图加起来超过 ~1MB，桌面就会把整块丢掉（这也是之前"主题显示不上"的原因）。
所以 4 帧只能共享约 4 万像素/帧：你那张 320×161dp 的卡在 3 倍密度下是 960×483 ≈ 46 万像素，
被压到 **300 多像素宽**，桌面再放大 3 倍 → 看起来就是糊。

## 为什么 SVG / 矢量图解决不了这个问题
矢量图能无限放大不失真，但它解决的是"缩放"，不解决"内容本身画了什么"：
- 这个主题的内容是**照片/二次元插画 + 粒子**，不是几何图形，没法用 SVG 表达（真转成 vector 路径，一个画面几万条指令，XML 比图片还大，桌面解码更慢）；
- 桌面小组件的 `ImageView` 通过 RemoteViews 只能拿 `setImageViewBitmap` / `setImageViewUri` / `setImageViewResource`；前两个都是位图，第三个是静态资源。**没有"把矢量交给桌面按需光栅化"的通道**；
- 真 60 帧、真矢量光栅化那条路只有动态壁纸（`DynWallpaperService`，App 内 60fps 渲染）—— 桌面 widget 不存在这条路。

## 真正的修法：绕开 binder
`ImageView.setImageUri` 是 RemoteViews 的合法方法。把帧**按卡片真实分辨率**渲染、落成 PNG，
再用 `FileProvider` 生成 `content://` URI 交给桌面 —— binder 里只传一个字符串，
桌面自己按文件原始分辨率解码。画质从"300 多像素宽"变成"960 像素宽"，提升 3 倍。

具体改动：
- `WidgetFrames.forSpec(..., fullRes = true)`：每帧 42 万像素预算、缩放上限 1.0（占内存是生成时的事，落盘后就不占）；
- 新增 `WidgetFrames.frameFiles()`：确保帧文件真的落盘（内存缓存命中的情况会强制重画一次，否则 URI 指空）；
- `TodayWidgetProvider.applyTheme`：高画质模式走 `setImageViewUri` + `setImageAlpha`（透明度），
  并且**底下压一张静态底图兜底** —— 万一某个桌面读不了 content URI，至少还有图，不会只剩文字；
- 有可读性遮罩时自动退回位图（幕要画进图里）。

## 开关
外观 → 桌面小组件 → **动态主题画质**：高画质（默认）/ 省内存。
省内存就是老路子（兼容性最好、会糊），留给你在个别桌面上试。

## 守这件事的用例
`WidgetHdFramesTest`：高画质帧宽度 ≥ 视图宽度的 95%、省内存帧不到高画质的一半（把"以前为什么糊"钉成断言）、
帧文件真的落盘且是 PNG（圆角靠透明角，JPEG 会填黑）、高画质默认开启。
