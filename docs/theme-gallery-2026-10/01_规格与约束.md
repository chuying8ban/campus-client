# 01 · 规格与约束

## 1. 平台基线（先核一遍，别凭印象）

| 项 | 值 | 出处 |
| --- | --- | --- |
| `minSdk` | 26（Android 8.0） | `app/build.gradle` 第 49 行 |
| UI | Jetpack Compose（App 侧） | `app/src/main/java/top/ccbase/campus/ui/**` |
| 小组件 | `RemoteViews` + `ViewFlipper` | `res/layout/widget_today_f_*.xml`（24 个字体变体）+ `widget_today.xml` |
| 现有动态主题 | 15 款，纯 `android.graphics` Canvas 绘制 | `widget/DynPainter.kt`（588 行） |
| 现有动态壁纸 | `WallpaperService` + `SurfaceHolder` 自己起绘制线程 | `widget/DynWallpaperService.kt` |
| 单测命令 | `./gradlew :app:testDebugUnitTest --offline` | `docs/RELEASING.md` |

**GLES 版本约束（关键）**：`RuntimeShader`（AGSL）要 API 33+，本 App 的 `minSdk` 是 26，所以**不能**把 AGSL 当主路径。主路径是 **EGL pbuffer + GLES 3.0 离屏渲染**（API 18+ 可用），AGSL 只做 33+ 的可选加速/预览。这条决定的直接后果：着色器要写 GLSL ES 3.00 源码，运行时编译（首次 30~80ms，需缓存 program）。

## 2. 现有阈值（不要重新猜，这些是踩过坑量出来的）

均来自 `widget/WidgetFrames.kt` 与 `widget/DynWallpaperService.kt` 的注释：

| 阈值 | 数值 | 后果 |
| --- | --- | --- |
| binder 单次事务上限（走 `setImageViewBitmap`） | ≈1MB 位图总量 | 超了桌面**整块丢弃小组件**（不是降级，是空白） |
| 高画质路径（`setImageViewUri` 落盘）总解码像素 | 630 万（24 帧 × 26 万） | 现在钉在这个数 |
| MIUI 桌面内存 | 全帧解码到 50MB 级会被回收 | 表现是「小组件一直在删来删去」 |
| 帧数 / 步长 | `FRAMES = 24`、`STEP_SEC = 0.25f` → 循环 6.0s | 每 6 秒肉眼可辨重复 |
| 翻转间隔 | `flipInterval="250"` | ≈4fps |
| 交叉淡入 | `res/anim/widget_frame_in.xml` / `out` 均为 200ms `accelerate_decelerate` | 80% 的时间在双重曝光 |
| 圆角 | `WidgetArt.radiusFor(hPx, density)` × scale，3.4.53 起 **16dp** | 帧必须 PNG（圆角带 alpha，JPEG 会把角填黑） |

## 3. 新预算表（本方案的目标值，替代上面的"现有"）

| 项 | 目标 | 说明 |
| --- | --- | --- |
| 帧数 `FRAMES` | **40**（日常款）/ **24**（招牌高清款） | 见 02 §2 |
| 步长 `STEP_SEC` | **0.20s** | 循环 8.0s（日常）/ 9.6s（招牌，0.40s） |
| 单帧像素上限 | **13 万 px**（日常）/ **26 万 px**（招牌） | 40×13万 = 520 万；24×26万 = 630 万 |
| 总解码像素 | **≤ 5.2M**（日常）/ ≤ 6.3M（招牌） | 沿用现有安全线 |
| `flipInterval` | **200ms** | 只允许 180~450ms |
| 交叉淡入 | **110ms**，`decelerate_interpolate` | 不要 200ms 满程 |
| 磁盘占用 | ≤ 6MB / 套（40 帧） | PNG 优先；WebP lossless 试一次，不行回退 |
| 烘焙耗时 | 首帧 ≤ 1.5s（先上桌），全套 ≤ 8s（后台补齐） | 渐进式，见 02 §5 |
| APK 增量 | ≤ 300KB | 着色器源码 + 参数表；素材走服务器 |
| 桌面内存增量 | ≤ 20MB | `dumpsys meminfo` 实测 |

## 4. 术语

- **烘焙（bake）**：把一套主题参数在后台渲染成 N 张位图，落盘成 `f0.png … fN-1.png`，桌面只负责按顺序显示。现有实现在 `WidgetFrames.frameFiles()`。
- **循环 T**：N × STEP_SEC，帧 N-1 接回帧 0 的周期。
- **闭合**：帧 N-1 与帧 0 的像素差 ≤ 相邻帧平均差 × 1.5。不闭合 = 每 T 秒硬跳一次。
- **准闭合**：允许元素相位在 3~4 个周期后漂移一个周期，用加长叠化（300ms）吸收那一次衔接。见 02 §3。
- **低频大形**：画面上没有硬边、没有高频细节、特征尺寸 >> 单帧位移的形态（雾、液态、光晕）。低帧率唯一能骗过眼睛的东西。
- **首帧上桌**：先用 8 帧粗糙版占位显示，全套烘焙完再静默替换。

## 5. 一份诚实的判断（写在这里免得后面反复争论）

- 桌面小组件**永远做不到**"视频壁纸"那种连续运动。它的上限是"看起来在缓慢呼吸、又看不太出是循环的静帧动画"。
- 能做到壁纸级的，是**画面本身**：景深层次、光溢出、暗角、颗粒、无 banding 的渐变。这四样做好，静态一张截图就已经比现在的动态款好看。
- 因此优先级是：**画面质量 > 循环结构 > 帧率**。反过来做（先堆帧数）是本末倒置。
