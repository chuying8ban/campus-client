## 二、和方案不一样的地方（以及为什么）

1. **没有上 GLSL 内核（方案 P1），改用 CPU fbm 流场。**
   方案假设可以靠 EGL + GLES 3.0 离屏烘焙。实际约束是：这一轮必须**不发真机也能验收**。
   GL 路径在国产 ROM 上失败只能表现为"整屏黑"，而我拿不到设备复验，风险不可接受。
   CPU fbm 在 480×270 上是 **62ms/帧**（40 帧 2.5s，Mac JVM 实测），烘焙在后台线程里完全够用，
   而且结果能在 JVM 测试里出图、人眼验收。等有真机时再上 GL，接口不用改：`FlowPainter.frame()` 就是边界。

2. **`DynPainter` 一个字节没删。** 粒子类（落樱/飘雪/流码/气泡…）继续走老画笔，
   只在 `FlowPainter.supports(kind)` 为真的款（极光/星云/丝绸/呼吸/潮汐/星轨）切内核。
   这就是方案里的"两条内核并行、老款保活"。

3. **40 帧的代价是"每帧更小"**：520 万像素 ÷ 40 = 13 万/帧，960×480 的卡上约 51% 宽度。
   方案 01 里写的"单帧 13 万"就是这个数。断言从"≥70% 宽度"改成"≥45% 且总量不超预算"。

4. **`meta.json` 是 JSON 字符串，不是文件结构体。** 校验逻辑仍是六项（kernel/spec/w/h/frames/step），
   但存成一行 JSON 更省事，也照样原子 rename。

## 三、已知没做完 / 没验证的

- **没有真机验证。** 设备在充电、用户睡下。所有"看起来变好了"的判断来自 JVM 渲染出的对照图
  （`app/build/preview/sheet.png`）+ 单测阈值，不是桌面实拍。
- **App 内主题没换成流场内核。** `Theme.kt` 的动态背景仍走 `DynPainter`；
  方案 03 要求"同一套内核、实时 GL"，这一轮没做。
- **信息层（方案 P4）没做**：等宽数字、8pt 栅格、玻璃层、按帧取色、天气/时段联动。
- **素材库还没做"从库里直接抽帧预览"**：选短视频时先烘一遍帧验证，慢了约 1~2s（小尺寸）。
- **丝绸款仍偏"布褶条纹"**：已经降到 0.9 的褶皱频率，但在 300×150 的缩略图上还是分得出发丝状脊线。
  真机上放大到卡片尺寸会柔和得多，需要一次实拍确认。
