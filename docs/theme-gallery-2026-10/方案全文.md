做四件事，按这个顺序：

| 序 | 做什么 | 为什么 | 涉及 |

| P3 | 画面内容换代：24~30 款"缓流 / 光晕 / 静图微动" | 低帧率只有低频大形能骗过眼睛 | 服务端 catalog + 素材 |

App 内主题（`DynamicBackground`）同一套内核、同一份素材，**但走实时 GL 60fps**，不再和小部件抢同一条"预渲染"的路 —— 见 `03_App主题改造方案.md`。

**一条必须接受的现实**：`RemoteViews` 在框架层面不存在 60fps（帧要经 `setImageViewUri` 交给桌面进程解码重绘，桌面自己还会节流）。因此"像 wallpaper 一样"只能落在两件事上：**画面质感**（可以做到壁纸级）和**感知流畅度**（靠运动幅度、闭合、叠化骗过眼睛，不是靠帧率）。任何"把帧率提到 30fps"的方案都是错的，别做。

## 四、红线（越了就是返工）

1. **不许提高桌面帧率**：`flipInterval` 只能落在 180~450ms 区间。低于 180ms 在国产 ROM 的 launcher 上会被节流或直接丢弃动画，表现比现在更差。
2. **不许把视频/GIF 直接塞进小组件**：解码 + 耗电 + 掉帧，且 `RemoteViews` 里没有可靠的视频播放路径。视频只允许出现在"烘焙源"里（先抽帧，再进管线）。
3. **不许直搬 Shadertoy**：默认 CC BY-NC-SA 3.0，禁商用，且要求同协议。学会思路、自己重写。
4. **不许用 Wallpaper Engine 创意工坊素材**：Steam 订阅协议限定在 Steam 客户端内使用，不能随 APK 分发。
5. **不许把 `DynPainter` 删掉或改签名**：App 与小部件都在调用它，它是回退路径。新内核并行存在。
6. **不许在广播/主线程做烘焙**：单帧 40 万像素的烘焙曾经就是"App 明显卡顿"的元凶（见 `WidgetFrames.ensureAsync` 注释）。所有烘焙走后台线程 + 落盘缓存。
7. **不许省略"版本号进缓存 key"**：换了内核不升级缓存版本，用户会一直看到旧帧（`existingFiles` 靠 `meta` 里的 stamp 比对，stamp 里没有内核版本）。

## 4. 术语

- **烘焙（bake）**：把一套主题参数在后台渲染成 N 张位图，落盘成 `f0.png … fN-1.png`，桌面只负责按顺序显示。现有实现在 `WidgetFrames.frameFiles()`。
- **循环 T**：N × STEP_SEC，帧 N-1 接回帧 0 的周期。
- **闭合**：帧 N-1 与帧 0 的像素差 ≤ 相邻帧平均差 × 1.5。不闭合 = 每 T 秒硬跳一次。
- **准闭合**：允许元素相位在 3~4 个周期后漂移一个周期，用加长叠化（300ms）吸收那一次衔接。见 02 §3。
- **低频大形**：画面上没有硬边、没有高频细节、特征尺寸 >> 单帧位移的形态（雾、液态、光晕）。低帧率唯一能骗过眼睛的东西。
- **首帧上桌**：先用 8 帧粗糙版占位显示，全套烘焙完再静默替换。

## 5. 一份诚实的判断（写在这里免得后面反复争论）

- 桌面小组件**永远做不到**"视频壁纸"那种连续运动。它的上限是"看起来在缓慢呼吸、又看不太出是循环的静帧动画"。
- 能做到壁纸级的，是**画面本身**：景深层次、光溢出、暗角、颗粒、无 banding 的渐变。这四样做好，静态一张截图就已经比现在的动态款好看。
- 因此优先级是：**画面质量 > 循环结构 > 帧率**。反过来做（先堆帧数）是本末倒置。

## 02 · 桌面小组件改造方案（重点）

## 1. 诊断：现在为什么"像幻灯片"而不是"像壁纸"

四条根因，按影响从大到小：

**① 画面构成是"渐变底 + 贴纸粒子"。**
`DynPainter` 的做法是：一张竖向渐变底图（`fillVertical`，缓存 1/4 分辨率）+ 若干 `glow()` 光团 + 一批随机粒子（`PETALS`/`SNOW`/`RAIN`/`MATRIX`）。这套画法在 60fps 下勉强能看，在 4fps 下必然崩——因为**粒子是高频小元素**，低帧率下它们只会"瞬移"。真正能撑住低帧率的只有低频大形：雾、液态、光晕、色场。

**② 空间层次是单一的。**
所有元素画在同一焦平面上。Wallpaper Engine 那类壁纸之所以"高级"，在于**景深**：前景虚、中景清、背景极虚，还有光溢出（bloom）和暗角。没有这四样，画面就是"平的"。

**③ 时间结构是"全屏同步 + 短循环 + 长叠化"。**
`FRAMES=24 × STEP_SEC=0.25 = 6.0s` 循环，`flipInterval=250ms`，交叉淡入 **200ms**。
- 200ms 淡入 / 250ms 间隔 = **80% 的时间都在双重曝光**。任何有硬边的元素都会抖成双影。
- 6 秒循环，人眼两三个循环就认出重复 → "这是段循环动画"的廉价感。

**④ 帧预算花在了错的地方。**
每帧 26 万像素（≈733×355）——为了"清晰"。但背景里没有文字（文字是独立 `TextView`），柔焦背景放大 1.5~2 倍根本看不出来。**这些像素应该换成帧数和循环长度。**

## 2. 目标画面形态（先定标准，再写代码）

一套合格的"壁纸级"静态帧，必须同时具备这五样，缺一样就是廉价感：

| 要素 | 具体要求 | 检查方法 |
| --- | --- | --- |
| 层次 | ≥3 个焦平面，前景模糊半径 ≥ 背景的 3 倍 | 缩到 25% 看，还能分出前后 |
| 光溢出 | 亮部周围有柔和辉光，不是硬边亮块 | 亮部边缘 3~5px 内有渐变衰减 |
| 暗角 | 四角压暗 8~14%，中心不被压 | 取四角/中心亮度比 |
| 颗粒 | 1.5~2.5% 强度的静态噪点（screen 空间，不随帧变） | 放大 200% 看有细颗粒，无条带 |
| 无 banding | 8-bit 输出必须抖动（Bayer 4×4 或三角噪声 1/2 LSB） | 深色渐变区放大看没有色阶台阶 |

**唯一豁免**：`grain` 必须在 screen 空间固定（同一套主题每帧噪点位置相同）。否则 5fps 下噪点会"闪"，比没有更糟。

## 3. 帧管线（数值与数学）

### 3.1 参数

| 参数 | 日常款 | 招牌款（≤3 款） | 依据 |
| --- | --- | --- | --- |
| `FRAMES` | 40 | 24 | 40 帧让单帧位移小到看不出步进 |
| `STEP_SEC` | 0.20 | 0.40 | 循环 8.0s / 9.6s |
| 单帧像素 | ≤13 万（≈480×270 于 16:9） | ≤26 万（≈680×380） | 总像素 520 万 / 630 万 |
| `flipInterval` | 200ms | 400ms | 只允许 180~450ms |
| 交叉淡入 | 110ms `decelerate` | 200ms `decelerate` | 叠化占比 55% / 50%，比现状的 80% 低一档 |

### 3.2 闭合数学（照抄这个条件，不要自创）

设循环 `T = FRAMES × STEP_SEC`。内核里任何一层元素的相位必须是：

```
phase_i(t) = 2π × ( k_i × t / T + φ_i )      k_i ∈ 整数, φ_i ∈ [0,1)
```

`k_i` 取整数 → 帧 N-1 接帧 0 时相位差恰好是 `2π × k_i`，**严格闭合**，无需额外处理。

**感知上"看不出循环"靠三件事，不靠加长 T：**

1. `k_i` 取值分散且互不成简单倍频：背景层 `k=1`，中景流体 `k=2`、`k=3`，前景光斑 `k=5`，涟漪 `k=7`。整幅画面的重复周期仍是 T，但**没有任何两个元素同时回到起点之后又同时离开**，眼睛抓不到"整帧重现"的锚点。
2. 位移幅度与 `k` 成反比：`k=7` 的那一层位移只有 `k=1` 的 1/5，看起来是"抖动"而非"循环"。
3. **循环内闭合 + 循环间变化由真实世界驱动**：整体色温/亮度按本地时间（早/午/晚/夜四档）与天气偏移，每 30 分钟或天气变化时重新烘焙。这样"每天看到的不一样"是真的不一样，不靠打破闭合去伪造。

**准闭合（仅用于招牌款，可选）**：若某一层用非整数 `k`（如 `k=2.5`）以获得更"自然"的运动，衔接处相位漂移半周期，此时必须把衔接那一次的叠化临时加长到 300ms 掩盖。**只有明确写注释、且只在招牌款用，日常款一律严格闭合。**

### 3.3 位移预算（防"步进感"的硬规则）

任一可见元素在 200ms 内的位移，**不得超过它自身特征尺寸的 1/3**。

计算方式：元素总行程 `S`，循环内来回 `k` 次 → 单帧位移 = `2·S·k / FRAMES`。举例：雾带横向行程 3% 屏宽、`k=2`、40 帧 → 单帧 0.3% 屏宽，肉眼完全看不出步进。反过来，若某元素单帧位移达到 2% 屏宽（如雪花下落），它在 5fps 下就是"瞬移"——**这类元素不许进小组件库**。

判定表（把现有 15 款按这个筛）：

| 现有款 | 判定 | 处置 |
| --- | --- | --- |
| `SILK` `DUSK` `BREATHE` `AURORA`(降速后) `NEBULA`(降速后) `BOKEH`(降速后) | 低频大形 | 保留思路，用新内核重画 |
| `PETALS` `SNOW` `RAIN` `MATRIX` `BUBBLES` `STARS`(星点闪烁) | 高频小元素 | **不进小组件库**；只保留在 App 内 60fps 与动态壁纸 |
| `RIPPLES` `WAVES` `FIREFLIES` | 边缘情况 | 降速 + 加大特征尺寸后可进，需逐帧验收 |

### 3.4 预算与落盘

- 帧文件：`cacheDir/wframes2/<presetKey>/f{N}.png` + `meta.json`。**目录从 `wframes` 改名为 `wframes2`**，避免读到旧内核的帧。
- `meta.json` 字段（替代现在那行字符串 stamp）：

```json
{
  "kernel": "gl2",
  "spec": "shader:liquid:ffa06bff",
  "w": 960, "h": 520, "speed": 1.0,
  "frames": 40, "step": 0.2,
  "built": 1750000000,
  "shaderHash": "a1b2c3d4"
}
```

`existingFiles()` 必须核对 `kernel`、`spec`、`w`、`h`、`frames`、`step`、`shaderHash` 六项，任一项不符即判失效重烘焙。**现在的 `stamp()` 里没有内核版本、也没有帧数，这两个必须加**，否则换代后用户永远看到旧帧、或者 24 帧目录被当成 40 帧读取（后半段全是空文件）。

- 压缩：API ≥30 用 `Bitmap.CompressFormat.WEBP_LOSSLESS`（带 alpha，比 PNG 小 25~35%）；API 26~29 回退 PNG。**不要用 JPEG**——圆角是透明的，会被填黑（这是 3.2.1 修过的坑）。

### 3.5 渐进式烘焙（体验关键）

一次烘焙 40 帧 × 40 万像素在低端机上要 6~10s，用户切主题后干等是不行的。

1. 切换瞬间：用**已缓存的同款 8 帧粗糙版**（或上一主题的首帧）先上桌，同时显示"正在生成"角标（`widget_flip` 旁边一个 `TextView`，2.5s 后自动隐藏）。
2. 后台线程按 `FRAMES` 均匀烘焙，**每完成 8 帧**就整目录原子替换一次（写 `meta.json.tmp` → rename），桌面最多看到 2 次跳变。
3. 全套完成 → 写最终 `meta.json` → `AppWidgetManager.notifyAppWidgetViewDataChanged` / 重新 `updateAppWidget` 触发一次刷新。

## 4. 渲染内核

### 4.1 架构

```
ui.theme / widget
   ↓ 参数（preset + accent + 时间档 + 天气档）
ShaderStudio (新增 widget/shader/ShaderStudio.kt)
   ↓ EGL pbuffer, GLES 3.0 离屏
GlProgram (新增 widget/shader/GlProgram.kt)   ← 编译/缓存/失败自检
   ↓ 4 个 pass
ShaderPreset (新增 widget/shader/ShaderPresets.kt) ← 每款主题 = 一段 GLSL + 一组 uniform
   ↓ Bitmap (RGBA8)
WidgetFrames (改) → 圆角 → WebP/PNG 落盘 → 桌面 ViewFlipper
```

**为什么保留两条内核并行**：`DynPainter` 是 15 款老主题 + 动态壁纸 + App 旧路径的实现，GL 在某些国产 ROM 上会失败（见 §8）。新内核只服务新图库，老款继续走老路。

### 4.2 Pass 设计（烘焙时不在乎实时性，可以多 pass 换质量）

| pass | 内容 | 分辨率 |
| --- | --- | --- |
| P1 `base` | 底色 + 大尺度色场 + 主光位置 | 1× |
| P2 `warp` | domain-warp 的 fbm 驱动流体/雾/液态；`k` 由 uniform 传 | 1× |
| P3 `blur` | 双层焦外：`fgBlur`（半径 8~14px）与 `bgBlur`（2~4px） | 0.5× 降采样后再升采样 |
| P4 `composite` | bloom（亮部阈值提取 + 3 级降采样模糊叠加）+ filmic 色调映射 + 暗角 + 色差 0.3px + 静态颗粒 + 抖动 | 1× |

### 4.3 参考着色器骨架（P2+P4 合并的简版，可直接作为起点）

```glsl
#version 300 es
precision highp float;
out vec4 fragColor;
uniform vec2  uRes;
uniform float uT;        // 秒，来自 bake 的帧序：i * step
uniform float uT0;       // 循环长度 T，所有相位必须用它做模
uniform int   uK;        // 该层循环次数（整数！）
uniform vec3  uTint;     // 强调色（线性空间）
uniform vec3  uBase;     // 底色
uniform float uGrain;    // 1.5% ~ 2.5%
uniform float uVignette; // 0.08 ~ 0.14

float hash(vec2 p){ return fract(sin(dot(p, vec2(127.1,311.7))) * 43758.5453); }

float noise(vec2 p){
    vec2 i = floor(p), f = fract(p);
    vec2 u = f*f*(3.0-2.0*f);
    return mix(mix(hash(i), hash(i+vec2(1,0)), u.x),
               mix(hash(i+vec2(0,1)), hash(i+vec2(1,1)), u.x), u.y);
}

float fbm(vec2 p){
    float v = 0.0, a = 0.5;
    for (int i = 0; i < 5; i++){ v += a * noise(p); p *= 2.03; a *= 0.5; }
    return v;
}

// 相位严格闭合：2π * (k * t/T + off)，k 必须是整数
float phase(float off){ return 6.2831853 * (float(uK) * uT / uT0 + off); }

void main(){
    vec2 uv = gl_FragCoord.xy / uRes;

    // —— 双向 domain warp：这是"液态/雾"质感的来源
    vec2 q = uv * 3.0;
    float t = phase(0.0);
    vec2 warp = vec2(fbm(q + vec2(0.0, t*0.15)), fbm(q + vec2(5.2, -t*0.12)));
    float f = fbm(q + 2.2 * warp);

    // —— 底色 → 流体 → 高光，三段映射（别用纯 mix，要有层次）
    vec3 col = mix(uBase, uTint * 0.55 + uBase, smoothstep(0.25, 0.75, f));
    col += uTint * pow(f, 3.0) * 0.35;             // 高光溢出感

    // —— 暗角
    vec2 d = uv - 0.5;
    col *= 1.0 - uVignette * dot(d, d) * 2.0;

    // —— filmic 近似（压高光，避免死白）
    col = (col * (2.51 * col + 0.03)) / (col * (2.43 * col + 0.59) + 0.14);

    // —— 静态颗粒（screen 空间固定，不随帧变！）
    float g = hash(gl_FragCoord.xy) - 0.5;
    col += g * uGrain;

    // —— 8bit 抖动：不做这一步，深色渐变必有 banding
    float bayer = fract(dot(gl_FragCoord.xy, vec2(0.7548776662, 0.5698402910)));
    col += (bayer - 0.5) / 255.0;

    fragColor = vec4(clamp(col, 0.0, 1.0), 1.0);
}
```

要点（写错就白做）：
- `uK` 必须是 **int**，且 `uT0` 传的是整套循环长度，绝不写死 6.0。
- 颗粒用 `gl_FragCoord` 落在 screen 空间，**同一套主题每帧噪点位置必须一致**。
- 别在 `sRGB` 空间直接做加法混色，会发灰；要么在线性空间算完再转，要么接受近似但保证对比度。
- 只有 5 个 octave 就够，多了烘焙时间线性增长。

### 5.1 排版规格

| 元素 | 规格 |
| --- | --- |
| 日期（"20"） | 44sp / w600 / **tabular figures（等宽数字）** / 行高 1.0 |

**tabular figures 是硬要求**：不开启的话，时间从 `9:41` 跳到 `9:42`、温度从 `11°` 跳到 `12°` 时整行会左右抖一下，一天几十次，比任何动效都毁质感。实现：`Paint.setFontFeatureSettings("tnum")`（API 21+）或字体本身带 `tnum` 特性。

### 5.2 玻璃层（零运行时成本的做法）

不要在运行时做实时模糊（`RemoteViews` 做不到）。**烘焙时就把 scrim 画进帧里**：

- 帧底部 30% 高度叠一层从 `#00000000` 到 `#0000002E` 的线性渐变；
- 文字区域中心再叠一层极淡的中心光（`#FFFFFF0A`，半径 = 卡片宽 40%），模拟"玻璃高光"。

这样文字永远可读，且不需要额外的 `View` 或 `Drawable`。

### 5.3 取色

从烘焙好的首帧取三处采样（左上 1/8、中心、右下 7/8），平均后转 HSL：

- `L > 0.55` → 用深色字族（`#1A1626` / 65% 不透明）；
- 否则用现有亮色字族（`WidgetTheme.headColor` 等）。

这套逻辑 `Theme.kt` 里已有近似实现（`rememberPhotoExtremes`），抽成工具函数复用，**不要复制第三份**。

### 5.4 真实世界联动（这是"别人抄不走"的部分）

| 输入 | 效果 | 实现要点 |
| --- | --- | --- |
| 本地时间四档（早/午/晚/夜） | 色温偏移 + 亮度 ±8% | 每 30 分钟一个 alarm 重烘焙（命中缓存则只换 meta，不重画） |

## 8. 性能与耗电

| 环节 | 预算 | 手段 |
| --- | --- | --- |
| 烘焙（40 帧） | ≤ 8s，峰值内存 ≤ 60MB | 逐帧 `Bitmap` 落盘后立即 `recycle()`，不整批留在内存（现有 `render()` 返回 `List<Bitmap>` 的做法在 40 帧 × 40 万像素下会到 64MB，**必须改成流式**） |
| 首帧上桌 | ≤ 1.5s | 粗糙 8 帧 / 缓存命中 ≤ 200ms |
| 桌面解码 | 总像素 ≤ 5.2M | 见 01 §3 |
| 桌面帧翻转 | 由 launcher 承担，App 进程零参与 | 保持 `ViewFlipper` 自翻，不要改回"App 主动推帧"（那条路已证明被节流） |
| 重烘焙频率 | ≤ 4 次/天（时间档）+ 天气变化 | 其余全部命中缓存 |

**流式烘焙的接口改动**（这是本方案里最容易做错的一处）：

```kotlin
// 现在：一次返回全部帧，调用方再落盘
fun frameFiles(...): List<File>?

// 改成：边烘边落，回调进度
fun bakeAsync(
    ctx: Context, spec: String, wPx: Int, hPx: Int,
    onProgress: (done: Int, total: Int, preview: File?) -> Unit,
    onDone: (files: List<File>) -> Unit,
)
```

## 9. 常见坑（按踩坑代价排序）

1. **改了帧数但没改 `existingFiles()`**：它硬编码 `(0 until FRAMES)`，而 `FRAMES` 现在是编译期常数。改帧数后索引越界或读到空文件 → 桌面显示空白，且**不报错**。必须先从 meta 读帧数。
2. **缓存 key 没有内核版本**：换代后用户永远看到旧帧（`meta` 里的 stamp 一模一样）。
3. **`recycle()` 与 `LruCache` 冲突**：现有 `ArtRepo` 有 `LruCache<String, Bitmap>` 缓存缩略图，如果烘焙路径复用了同一批 Bitmap 又 recycle，会抛 `Canvas: trying to use a recycled bitmap`。流式烘焙的 Bitmap **不进任何缓存**。
4. **`ViewFlipper` 在 launcher 被回收重建后从 f0 开始**：这是正常的，不要试图持久化播放位置（`RemoteViews` 没法控制）。
5. **24 个 layout 漏改一个**：用字体变体的用户会看到"别的都 200ms、就我这套 250ms"。必须用单测遍历 `res/layout/widget_today_f_*.xml` 校验。
6. **PNG 体积暴涨**：40 帧 × 480×270 的雾状渐变 PNG 可能每张 300KB（噪点会让 PNG 几乎压不动）。加了颗粒之后**必须重测体积**，超 6MB 就把颗粒强度降到 1.2% 或改用 WebP。这是个真实的陷阱，别到最后才发现。
7. **圆角必须画在帧里**：`RemoteViews` 没有圆角属性，`WidgetArt.rounded()` 这一步不能省，半径用 16dp × scale，和静态主题保持一致（否则"有的方有的圆"，3.4.53 修过一次）。

## 03 · App 主题改造方案

> 关联代码：`ui/theme/DynamicBackground.kt`（249 行）、`ui/theme/DynThumb.kt`、`ui/theme/Theme.kt`、`ui/theme/UserMedia.kt`、`ui/me/ThemeSection.kt`（871 行）、`ui/me/AppearanceScreen.kt`（903 行）。

## 0. 一条总原则

**App 内与桌面小组件必须是同一套视觉。** 同一个主题 id，在 App 里看到的和桌面上看到的要是同一幅画，只是 App 里流畅、桌面上慢。做法是共用 `ShaderPresets` 的参数表与 GLSL 源码，只是 App 走实时渲染、桌面走烘焙。任何"App 一套素材、桌面另一套"的做法都会在用户截图对比时暴露。

---

## 1. 现状与三个具体问题

**① 图库是 90 宫格，用户挑不过来。**
`DYN_PRESETS = DynKind.entries × DYN_TINTS` = 15 × 6 = **90 款**（`DynamicBackground.kt` 第 240 行，注释还写着"12 种 × 6"，已过期）。这 90 款里有一半是同一幅画换色，用户滑两下就放弃，且会觉得"都是差不多的东西"。

**② 实时绘制占用 UI 线程。**
`DynamicBackground` 用 Compose `Canvas` + `withFrameNanos`，每帧在 UI 线程跑一遍 `DynPainter.frame()`。虽然加了"连续 20 帧掉速就降到 30fps"的自适应（第 107~134 行），但那只是止损——**根因是背景和列表在抢同一帧的预算**。上 GL 之后背景有自己的线程，这个问题从架构上消失。

**③ 缩略图和正片不是同一套实现。**
`DynThumb.kt` 用 `DynPainter.frame(c, kind, 3.7f, ...)` 画一张静态缩略。换了新内核后，如果缩略还走老画笔，图库里就会"缩略是一个样、点进去是另一个样"。

---

## 2. 实时 GL 集成（App 内 60fps）

### 2.1 容器选择

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| `GLSurfaceView` + `AndroidView` | 独立渲染线程、成熟、掉帧不影响 Compose | z-order 与裁剪要靠 `setZOrderOnTop` 调；部分 ROM 上圆角裁剪失效 | **主选**（背景铺满、不需要裁剪） |
| `TextureView` | 能参与 Compose 变换/圆角/动画 | 多一次 GPU→CPU→GPU 拷贝，功耗高 15~20% | 备选，用于需要裁圆角/做转场的场景 |

放在页面最底层：`Box { GlBackground(...); content }`，`glSurface.setZOrderMediaOverlay(false)`。

### 2.2 生命周期与暂停（省电的关键）

```kotlin
// 三条状态必须都处理，缺一条就是"后台还在烧电"
onResume / onPause          → glSurface.onResume() / onPause()
Compose 可见性（LazyColumn 滚出、页面被覆盖） → requestRender 停
屏幕熄灭（ACTION_SCREEN_OFF） → 停渲染线程
```

绘制用 `RENDERMODE_CONTINUOUSLY` 但内部自己做节流：以 vsync 为准（`eglSwapBuffers` 本身会阻塞到刷新），**不要再加 delay**（现在的 33ms 定长 tick 正是"一顿一顿"的来源，注释里已经记过这个教训）。

### 2.3 尺寸与密度

- 渲染分辨率按 `min(1.0, 1080f / height)` 缩放：1080p 屏 1.0，1440p 屏 0.75，既保住观感又省一半像素。
- `onSurfaceChanged` 里重建 framebuffer，**不要**在每帧里判断尺寸变化。
- 高刷屏（120Hz）要限制到 60fps：`eglSwapInterval(1)` 在两倍刷新率下会跑 120fps，功耗翻倍。用 `Choreographer` 每两帧提交一次，或设 `eglSwapInterval(2)`（设备行为不一致，优先用 Choreographer 计数）。

### 2.4 与滚动联动（App 独有的高级感）

App 内能做到而小组件做不到的两件事，值得做：

1. **视差**：列表滚动 `firstVisibleItemScrollOffset` → 背景 `uv.y += offset * 0.0008`（幅度上限 4%）。滚动时的"深度感"是壁纸级观感里最便宜的一档。
2. **转场**：从图库点选主题 → 新主题从点击位置以半径扩散切入（GL 里一个 `uReveal` uniform，0.45s），替换现在的硬切。

## 3. 图库结构重构（90 → 24 + 调色）

### 3.1 新结构

```
外观 → App 主题
├─ 精选（24 款，横滑大卡，真首帧预览）
│   ├─ 缓流 fluid：液态 / 丝绸 / 雾霭 / 极光 / 沙丘 / 水面折射 / 熔岩灯
│   ├─ 光晕 glow：地平线 / 云隙光 / 霓虹雾 / 单光源呼吸 / 焦外光斑 / 星云
│   └─ 静图微动 still：摄影 6 款（Ken Burns + 视差 + 颗粒）
├─ 调色（选中后进二级页：6 色系 + 明暗两档）  ← 替代现在的 90 宫格
├─ 动态壁纸（"设为壁纸"入口，见 §5）
└─ 经典（折叠区，15 款老的 DynPainter 款，标"经典"）
```

**为什么这样分**：用户挑的是"画面"，不是"参数"。先给 24 张一眼能选的画面，色系收进二级页——**选择成本从 90 降到 24，且不减少实际可选组合（24×6=144）**。

### 3.2 数据模型

```kotlin
// 新：一条主题 = 一个 shader preset，色系是可调参数而非独立条目
data class ShaderTheme(
    val id: String,            // "liquid"
    val name: String,          // "液态"
    val group: Group,          // FLUID / GLOW / STILL
    val tags: String,          // 搜索用："流动 液态 玻璃 极简"
    val defaultTint: Int,
    val animated: Boolean,     // 静态素材为 false，卡片上不打"动"角标
)
```

`ArtItem`（`ArtLibrary.kt`）已经有一个 `animated: Boolean` 字段，语义保留；新图库的条目要么是 `ShaderTheme`（程序化），要么是 `ArtItem`（服务器图）。**两条流合并展示，但筛选项分开**（程序化 / 图库）。

### 3.3 预览必须是"真帧"

- 程序化款：进入可见区域时用离线 GL 烘一帧 320×180 的缩略（一次，落盘缓存，key 带 shaderHash），**不要**用老 `DynPainter` 画。
- 图库款：用 `ArtItem.thumbUrl`。
- 卡片右下角标：`动` / `静` / `需下载`。用户 2026-10-18 明确要求过动态内容要标注。

### 3.4 搜索

保留现有按"标题/标签/id"匹配的本机搜索（`ArtRepo` 的做法），但 haystack 要把 `name + tags + group` 都放进去。搜索页不再展示 90 款，只展示 24 + 服务器条目。

## 4. spec 与存储迁移

现有 spec 前缀（都在 `DynamicBackground.kt` / `WidgetTheme.kt`）：

| 前缀 | 含义 | 新方案 |
| --- | --- | --- |
| `anim:<kind>:<argb>` | 老的 15 款程序化 | **保留可用**，归到「经典」折叠区 |
| `animphoto:<effect>` | 静图 + Ken Burns + 粒子 | 保留，升级参数（见 §6） |
| `preset:` / `photo` / `solid` | 静态主题 | 不动 |

- 新装用户默认 `shader:liquid`。
- 落盘位置沿用现在的 `bgChoice` 偏好项，不新增迁移逻辑。

## 5. 动态壁纸（`DynWallpaperService`）

现状：它已经用 `SurfaceHolder` + 自己的绘制线程跑 `DynPainter.frame()`，是 App 里唯一真 60fps 的地方。

改造：

1. 引擎里加一条分支：主题是 `shader:` 款 → 用 GL 渲染到 wallpaper 的 Surface（`EGLSurface` 直接从 `SurfaceHolder.getSurface()` 建），而不是 `Canvas`。
2. 保留 `DynPainter` 分支给经典款。
3. 进入壁纸后不可见时（`onVisibilityChanged(false)`）必须停线程——这是壁纸耗电的第一大来源。
4. 壁纸侧的 `uRes` 要按屏幕真实像素（含导航栏区域），不能用 App 的渲染缩放。

## 6. 静图微动（`animphoto` 的升级）

现在是 `zoom = 1.03 + 0.03 * sin(t/3.2 * 2π)`——周期 **3.2 秒**，太快，像"呼吸急促"。改成：

| 参数 | 现在 | 改成 | 理由 |
| --- | --- | --- | --- |
| 推近周期 | 3.2s | **12s** | 壁纸级的推拉是"几乎察觉不到" |
| 缩放幅度 | ±3% | **±2%** | 幅度小才不晕 |
| 位移 | 1.2% / 1.0% | **0.6% / 0.5%**，周期 12s / 18s（不同频） | 双频叠加去掉"往复"感 |
| 前景粒子 | `DynPainter.particles` 0.6 强度 | 只在 `PETALS/SNOW/FIREFLIES` 三种保留，强度 0.35，速度 ×0.6 | 低强度前景粒子才像景深，不像贴纸 |
| 新增 | — | 颗粒 1.5% + 暗角 10% + 边缘虚化（径向模糊 2px） | 让照片有"镜头"味 |

边缘虚化用 Compose 做不了，得走 `RenderEffect`（API 31+）或直接用 GL 后处理；API <31 的设备跳过这一步，不要用 `RenderScript`（已弃用）。

## 9. 坑

1. **`GLSurfaceView` 在 Compose 的 `AndroidView` 里被重建**：`key` 要写死，且 `onRelease` 里必须 `onPause()` + 释放 EGL，否则退出页面后 GPU 上下文泄漏，第二次进来黑屏。
2. **`setZOrderOnTop(true)` 会让背景盖住文字**——只允许 `setZOrderMediaOverlay`，且必须在 `AndroidView.factory` 里设置（晚了不生效）。
3. **GL 线程里不能碰 Compose state**：所有 uniform 通过 `AtomicInteger/AtomicReference` 传，不要 `mutableStateOf`。
4. **`rememberDynTime` 的教训别丢**：任何"定长 delay 循环"都会和 vsync 错位。新代码一律以 `eglSwapBuffers`/`Choreographer` 为准。
5. **缩略图缓存不能存 GL Bitmap 之外的引用**：`ArtRepo.thumbs` 是 `LruCache<String, Bitmap>`，塞进去的 Bitmap 不能被 recycle（见 02 §9 第 3 条）。
6. **旧款不许删**：`anim:` 那 15 款有用户在用，删了等于把人家桌面变黑（`DynPainter` 里已有"很多动态主题根本用不了、用了之后变成纯黑"的历史教训）。

## 2. 帧质量脚本（这是本方案的核心验收工具）

新增 `tools/check_frames.py`（系统 python3 + Pillow 即可，本机已有）：

```python
#!/usr/bin/env python3
"""校验烘焙出的帧序列：闭合、叠影、体积。用法：python3 check_frames.py <帧目录>"""
import sys, os, json
from PIL import Image, ImageChops, ImageStat

d = sys.argv[1]
meta = json.load(open(os.path.join(d, "meta.json")))
n = meta["frames"]
frames = [Image.open(os.path.join(d, f"f{i}.png")).convert("RGB") for i in range(n)]

def diff(a, b):
    return ImageStat.Stat(ImageChops.difference(a, b)).mean[0]

consec = [diff(frames[i], frames[(i + 1) % n]) for i in range(n)]
wrap = consec[-1]                      # 帧 n-1 → 帧 0
avg = sum(consec[:-1]) / (n - 1)
size_mb = sum(os.path.getsize(os.path.join(d, f"f{i}.png")) for i in range(n)) / 1e6

print(f"帧数 {n}  平均相邻差 {avg:.2f}  闭合差 {wrap:.2f}  总体积 {size_mb:.1f}MB")
ok = True
if wrap > avg * 1.5:
    print(f"✗ 不闭合：闭合差 {wrap:.2f} > 平均相邻差 {avg:.2f} × 1.5，桌面每轮会硬跳一次"); ok = False
if max(consec) > avg * 3:
    print(f"✗ 存在跳帧：最大相邻差 {max(consec):.2f} > 平均 × 3"); ok = False
if size_mb > 6:
    print(f"✗ 体积超标 {size_mb:.1f}MB > 6MB（颗粒强度或分辨率要降）"); ok = False
if min(consec) < 0.15:
    print(f"⚠ 最长静止变化 {min(consec):.2f} 过小：可能有几帧几乎一样，等于浪费帧预算")
print("PASS" if ok else "FAIL")
sys.exit(0 if ok else 1)
```

**通过线**：闭合差 ≤ 平均相邻差 × 1.5；最大相邻差 ≤ 平均 × 3；总体积 ≤ 6MB。

## 6. 发版前的三条硬核验

按 `docs/RELEASING.md` 走，另外本方案额外要求：

1. **APK 增量 ≤ 300KB**：`unzip -l` 对比上一版，shader 源码与参数表不能吃包。
2. **首启不卡**：清数据 → 首次进入外观页，GL 初始化（含 program 编译）≤ 400ms，期间不黑屏。
3. **回滚可用**：把 `shader_ok` 手动置 false，图库仍能用经典款，不崩。
