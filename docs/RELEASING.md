# 发版须知

给以后维护它的人（很可能就是几个月后的你）。发一次新版要做的事一次列清，漏掉哪一步、后果是什么都写在旁边。

**本文件只讲公开面**：怎么构建、怎么签名、怎么发出一条所有人都能下载/更新的新版。运维侧的事（服务器上那个目录怎么布、后台怎么管）不在这里，见仓库外的运维手册。

## 一次发版 = 三条公开通道同时更新

| 通道 | 给谁 | 做什么 |
| --- | --- | --- |
| GitHub Release | 新用户下载 | 上传 `campus-<版本>.apk`，写清安装步骤、非官方声明、抢课免责 |
| 服务端 `/updates/manifest.json` + 同目录下的包 | 已装用户（App 内「我的 → 检查更新」） | 换 manifest 的 `version_code` / `version_name` / `url` / `sha256` / `size`，并把新包放到 `url` 指的位置 |
| 服务端 `/updates/latest.apk` 稳定别名（软链） | 下载页 / 拿不到清单时的兜底 | 重新指向新包 |

**一次发版要同时换这三处**：新包、manifest 的版本号+sha256+size、`latest.apk` 软链。漏前两处，已装用户看不到更新提示；漏 `latest.apk`，走下载页的人拿到旧包。

只做 GitHub：老用户永远收不到提示。只做服务端：新用户找不到下载入口。**旧包在服务端留着**，老用户才不会断。

**每次发版都要在 App 内可见**：换 manifest 版本号不是可选项——不换，用户在新版发布后打开 App 只看得到"已是最新"。

## 版本号

- `versionCode` **只增不减**：更新判定是「清单里的号 > 当前装的号」，号不涨的包在用户设备上不会被视为更新（静默不动，界面上也看不出问题）。
- 同一个 `applicationId` 才能覆盖安装；换包名等于另起一个 App，用户的本地数据不会跟过去。
- 打包脚本里那句"版本号改过了"**别只信它自己的打印**：改完要**回读磁盘上的 `app/build.gradle`** 核对（名字 + 号），对不上就停。同类教训：更新说明也曾被"打印成功但其实没改"骗过一次。

## 签名

- 所有对外发布的包用**同一把 keystore**（本仓发布线的证书 SHA-256 前 8 位 `6eb42692`）。换钥匙意味着已装用户必须先卸载，本地数据一起丢。
- 口令只放受控文件（本机 `local.properties` 或 `~/.config/` 下的 600 文件）：**不进仓库、不进命令行参数、不进聊天**，构建脚本从文件或环境变量读。
- 每次打包后必核：`apksigner verify --print-certs` 的证书 SHA-256 **逐字符等于基准**，不等就停、不上传。

## 自己构建一个包（fork 之后这么走）

1. `local.properties`（已 gitignore）写：`sdk.dir=<你的 Android SDK>`、`apiBase=https://<你的后端>`、`campusKeystore=` / `campusStorePass=` / `campusKeyPass=`（自己生成的 keystore 与口令）。
2. `./gradlew :app:testDebugUnitTest --offline` 全绿，再 `./gradlew :app:assembleRelease`。
3. `apksigner verify --print-certs` 确认用的是**你自己的**证书——换钥匙的用户装不上你的包，这是安全特性不是 bug。
4. 公开仓默认**没开代码压缩**（`minifyEnabled false`）。想开就自己开，但那意味着要重新过一遍"包里没有不该有的字符串"。

## 发版顺序

1. 改代码 → 跑**全部单元测试** → 文档与代码**同一个 commit**（文档不进 APK，但仍在最终 HEAD 上记一次指纹）。
2. 打包；**验签**等于你发布的证书。
3. 把包放上服务端、换 manifest、换 `latest.apk`（三处一起）。
4. 建 GitHub Release：正文**只放发布内容**（别把维护者说明、占位符提示那份草稿直接当 `--notes-file` 发出去，它会被原样公开）；附上 sha256、大小、签名证书前 8 位。
5. 回读校验：Release 附件能下载且 sha256 与打包件一致；manifest 的版本号与包一致；已装用户点「检查更新」能看到新版本。
6. **产物不是逐字节可复现的**：换了构建机、或重打一次包，`sha256` 必须**重取**，别沿用上一次那个数；发出去之前用**最终那个文件**自己算一遍，再写进 Release 正文。

## 更新说明（notes）怎么写

App 的更新面板是一行一条（每条一个圆点），所以文案本身就是结构：

- **一件事一条**，别把几件事挤成一条长句；每条控制在 40 字内。
- **不要写版本号/渠道前缀**（"公开版 1.85：…"）——面板上方已经写着"需要更新到 x.y"。
- **只写真实做得到的事**：例"新增抢课"会被读成"它能替我抢课"，而实现只是余量监控与提醒；GitHub Release 正文里的免责说明与这里要对得上。
- 改完**自己拿真清单读一遍**（用户看到的就是那份），别只对着草稿看。

## 更新通道的隐私隔离（发布前必核）

更新是**匿名**的：服务端不需要知道"是谁在更新"，也不该知道。发布前逐条核过，缺一条就是一句站不住的隐私声明：

- [ ] manifest 与 APK 两条 URL **不带 token、不带学号、不带任何用户标识**；不要加 `uid` 之类的查询参数，也不要按用户区分路径。
- [ ] 客户端请求更新时**不附带登录令牌或账号字段**：版本检查发的是空 header + `token = null`，APK 下载那条连 header 参数都不存在。检查 URL 上那个 `?t=<毫秒>` 是**防缓存**用的，**别以隐私为名删掉**——删了用户就再也收不到更新提示；它只含毫秒时间、不含身份。
- [ ] 服务端侧：`/updates/*` 是 nginx 直发的静态目录，应用不参与；访问日志是默认 combined 格式，字段为 **IP / 时间 / 方法+URL+协议 / 状态 / 字节数 / referer / UA**，不含 uid、不含令牌、不按用户分路径。→ 这条声明的边界是：**来源 IP 与 UA 会被记录**（任何网站都会），所以写文档时写"不知道是谁在更新"，**别写"什么都不记"**。
- [ ] 发布后从公网各取一次 manifest 与 APK，核对 URL 里没有任何用户标识，且没有多出按用户区分的落点。

## 文档

- `README.md` 与 `README_EN.md` 同步改，两版必须说同一件事；发版后回读**渲染后的页面**（语言互链、相对链接、LICENSE 是否被判成 MIT、About 的描述与 topics 是否生效）。
- 隐私与安全类声明只写能在代码或实测里指出来的话；写不了的（"不会写进任何日志"这类绝对句）不要写。
- 版本号、用例数这类会漂的数字不要写死在正文里——要留痕迹就写清它属于哪一次。
- **给发布用的文件只能装发布内容**：维护者说明、占位符提示另放一个文件，否则 `gh release create --notes-file <草稿>` 会把它们原样发到公开页。
- **服务端返回的 `detail` 是直接给同学看的话**：任何一条都**不许包含对用户身份或操作的怀疑**（"可能不是本校账号""密码错了吧"这类是把系统状态压成用户过失），也别说"请联系作者"（作者修不了教务系统）；要写就写清是什么状态、会不会自动重试，别承诺具体时间。这类字符串改动前先在 fixture 上干跑一遍再上线。
- 界面/日志/清单里出现的每句话，都要能被用户自己在那一刻看到的现象验证。
